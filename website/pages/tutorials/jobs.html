Jobs that step aside: your own workstation on a shared cluster

Put a training into the queue. It runs on every node nobody has booked, saves a checkpoint when someone needs a node, and continues elsewhere with your home and its name. You log in to train42.mesh as if it were your own machine, wherever it runs.

You need: a network with bookable GPU nodes and a gateway (Book a test bench), rsync on the nodesVersion: meshvpn enterprise 0.17 or newer

Steps

1. What happens 2. Make your training resumable 3. Turn on the scheduler 4. Submit a job 5. Log in by its name 6. When someone books 7. Homes for each purpose 8. Good to know

STEP 1

What happens

A job is a command, a user, and how many nodes of which kind it needs. The scheduler, the portal or an admin node, places it as soon as enough nodes are free: online, allowed for the user by a device rule, running no other job, and not booked by someone else now or in the next 10 minutes.

WhenThe jobYou
Nodes are freeruns, as you, in your homessh train42.mesh, sudo if the device rule allows it
Someone books one of its nodesgets a stop request, saves its checkpoint, waits in the queuenothing to do
Nodes are free againyour home comes to the new first node, the job resumes from the checkpointssh train42.mesh again: same name, same files, no warning
It's doneits name goes, your home stays where it ranresults are in your home

Bookings always win. That is what makes the queue safe for everyone: people who need a machine get it, and the GPUs that would sit idle in between run queued jobs.

STEP 2

Make your training resumable

When the job should stop, the file $MESHVPN_STOP_FILE appears on each of its nodes. Your training saves a checkpoint and exits. The next run starts the same command again, with MESHVPN_RESUME=1, and loads the latest checkpoint. Most training frameworks can resume from a checkpoint already; you only add the stop check.

train.py (PyTorch, any number of nodes)
import os
import torch
import torch.distributed as dist

ckpt_dir = os.environ.get("MESHVPN_CHECKPOINT_DIR", "checkpoints")
stop_file = os.environ.get("MESHVPN_STOP_FILE", "")
latest = os.path.join(ckpt_dir, "latest.pt")
os.makedirs(ckpt_dir, exist_ok=True)

dist.init_process_group("nccl")
rank = dist.get_rank()
torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))
model, opt = build_model(), build_optimizer()  # yours

step = 0
if os.path.exists(latest):  # from the second run on (MESHVPN_RESUME=1)
    state = torch.load(latest, map_location="cpu")
    model.load_state_dict(state["model"])
    opt.load_state_dict(state["opt"])
    step = state["step"]
    print(f"resuming from checkpoint step-{step}")

def should_stop():
    # Each rank sees its own node's stop file; all ranks stop at the same step.
    flag = torch.tensor([int(bool(stop_file) and os.path.exists(stop_file))], device="cuda")
    dist.all_reduce(flag, op=dist.ReduceOp.MAX)
    return bool(flag.item())

while step < TOTAL_STEPS:
    train_step(model, opt, step)  # yours
    step += 1
    stop = step % 50 == 0 and should_stop()
    if stop or step % 1000 == 0:
        if rank == 0:
            torch.save({"model": model.state_dict(), "opt": opt.state_dict(), "step": step}, latest + ".tmp")
            os.replace(latest + ".tmp", latest)
        dist.barrier()
    if stop:
        break  # exit 0: the job goes back into the queue

dist.destroy_process_group()

Rank 0 runs on the job's first node, which holds your home, so the checkpoint is in the home that moves. Checking the stop file every 50 steps keeps the all-reduce cheap; pick a number that stays well within the grace period (2 minutes by default).

Not PyTorch? Anything works that saves its state and exits when the file appears. A shell loop: [ -f "$MESHVPN_STOP_FILE" ] && { save; exit 0; }. Programs that prefer a signal get one with --signal USR1 (careful with torchrun: it doesn't handle USR1 itself).

STEP 3

Turn on the scheduler

One admin node places jobs and signs the nodes' SSH host certificates. In networks the portal manages, the portal does it by itself. Without a portal, pick an admin node that is always on:

on the admin node
$ sudo meshvpn job scheduler enable
adm schedules jobs and signs host certificates

The network now has its own SSH host CA. The portal's Workspace shows each user the line to add, with a copy button (and meshvpn job list prints it) to their ~/.ssh/known_hosts once, so that ssh trusts every node by its certificate, also after a job moved:

on your laptop, once
$ echo '@cert-authority *.mesh ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA...' >> ~/.ssh/known_hosts

STEP 4

Submit a job

Users do it themselves in the portal: Workspace → New job (nodes, how many, a name, the command, which home). Agents use the same API with their key:

$ curl -H "Authorization: Bearer mvk_..." -H "Content-Type: application/json" \
       -d '{"network":"cluster","select":"tag:a100","count":4,"name":"train42","command":"torchrun --nproc_per_node 8 train.py"}' \
       https://portal.example.com/api/jobs

Or an admin on the command line:

on the admin node
$ sudo meshvpn job submit tag:a100 --count 4 --user alice --name train42 \
      --workdir projects/llm -- torchrun --nproc_per_node 8 train.py --config exp42.yaml
job train42 (j3f9c21a0) for alice: 4 node(s) of tag:a100: torchrun --nproc_per_node 8 train.py --config exp42.yaml
$ meshvpn job list
NAME           ID         USER       STATE              WHERE
train42        j3f9c21a0  alice      running for 3m     run 1 on a100-1, a100-2, a100-5, a100-6

torchrun gets --nnodes, --node_rank, --master_addr and --master_port for the current nodes added; every run gets MASTER_ADDR, NODE_RANK, NNODES and the NCCL interface. Other options: --grace 5m (time to save), --signal USR1, --home and --temp-home (step 7).

The output of each run goes to ~/.meshvpn/jobs/<id>/run-<run>-<node>.log in the job's home. meshvpn job show train42 lists every run with its nodes and why it ended.

STEP 5

Log in by its name

train42.mesh points to the job's first node on every node of the network, the gateway included. Alice's ~/.ssh/config from Book a test bench works unchanged:

alice's laptop
Host *.mesh
    ProxyJump jump@gw.example.com
$ ssh alice@train42.mesh
alice@a100-1:~$ nvidia-smi; tail -f projects/llm/train.log

While the job runs on a node, alice has her account there, with sudo if the device rule allows it, just like during a booking. VS Code Remote, scp and rsync to train42.mesh work the same way.

STEP 6

When someone books

$ sudo meshvpn book a100-1 a100-2 --user bob --for 3h
  1. The scheduler sees the booking coming and asks train42 to stop: the stop file appears (and the signal, if you asked for one).
  2. The training saves its checkpoint and exits. After the grace period, what's left gets SIGTERM, 15 seconds later SIGKILL.
  3. The job goes back into the queue and is placed on free nodes: the two it kept (a100-5, a100-6, they ran it before) and a100-3, a100-4.
  4. Alice's home comes to the new first node, only what changed. The run starts with MESHVPN_RESUME=1 and resumes from the checkpoint.
  5. train42.mesh now points to the new first node. Alice's next ssh lands there, without a host key warning.

If the job is still saving when the booking starts, bob shares the node with it for at most the grace period. Book a few minutes ahead and the node is free when you arrive.

STEP 7

Homes for each purpose

Every user has the home default (/home/alice, where logins land). It always stays. Next to it, homes for projects or experiments live under ~/homes/<name>, and each has its own rules:

# a home for one experiment, deleted with all its copies when the job is done
$ sudo meshvpn job submit tag:a100 --count 4 --user alice --temp-home -- torchrun train.py
# a project home: old copies on nodes it left go after 30 days
$ sudo meshvpn home add llm --user alice --stale 30d
$ sudo meshvpn job submit tag:a100 --count 4 --user alice --home llm -- torchrun train.py
$ sudo meshvpn book a100-7 --user alice --home llm --for 2h
$ meshvpn home list --user alice
USER         HOME         ON         COPY       STALE    RULES
alice        default      a100-3     a100-8     7d
alice        llm          a100-7     a100-2     30d      in use
RuleOptions
Copies on nodes the home has left--stale 7d (default), --stale delete, --stale keep
An extra copy on another node, refreshed every 5 minutes while in use--copies 1 (default), --copies 0
Lifetimepermanent, --with-job train42, --expires +30d

A home lives where it was used last: if you continue on the same node, nothing is copied. The extra copy keeps it available when its node is offline or booked by someone else.

STEP 8

Good to know

  • Multi-node jobs: the first node holds the home; the others get a copy at the start, and what they write into it isn't kept. Write checkpoints from rank 0, and shared results to the first node or shared storage.
  • Datasets don't belong in a home that moves: keep them on every node (meshvpn share and fetch spread them fast) or on shared storage.
  • Cancel with sudo meshvpn job cancel train42: the job gets the stop request and its grace period first.
  • Whole nodes: a job uses its nodes exclusively. Several jobs on one node's GPUs come later.
  • Your own accounts on a machine (not created by meshvpn) are never touched: their homes don't move and aren't deleted.
