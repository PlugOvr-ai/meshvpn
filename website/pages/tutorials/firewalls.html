Behind NAT and firewalls

Lab machines rarely sit on the open internet. This tutorial shows how meshvpn reaches nodes behind home routers, mobile networks, corporate firewalls and SSH-only jump hosts, and how to send internet traffic through another node.

You need: a network from Your first networkWorks on: Linux; status and connect also on macOS and Windows

Steps

1. How paths are found2. Read the NAT type3. Open UDP 7870 4. Only SSH out5. Network behind a firewall6. No internet at all 7. Exit nodes

STEP 1

How paths are found

Nodes keep TCP links for control traffic, because TCP is what SSH tunnels and proxies can carry. For data, they try to open direct UDP paths:

  • Each node publishes its address candidates: LAN addresses, its public address as other nodes see it, and IPv6 addresses.
  • Both sides send authenticated probes to each other. That opens a path through both NATs (hole punching).
  • Data then goes directly over UDP. The LAN is preferred, then IPv6, then IPv4 through NAT.
  • If a path stops answering, traffic falls back to TCP or to a relay through another node within seconds.

Relays can't read or change the traffic: it is encrypted end to end between the two nodes.

STEP 2

Read the NAT type

meshvpn status shows the path to each node and what kind of NAT this node is behind:

$ meshvpn status
● laptop  100.122.64.143  (ef5a9cd4 on mesh0, network "lab")
  NAT (IPv4):   behind NAT that changes the port per destination (typical for mobile networks) - direct IPv4 paths only to nodes that are reachable from outside
  IPv6:         2a02:3100:…:7c1 (direct paths through firewalls)

NAME     IP               STATUS      RTT  PATH
vps      100.94.140.208   online     12ms  direct UDP 178.77.77.96:7870
labbox   100.92.238.33    online        -  relay via vps
NAT typeWhat it means
public addressNo NAT. Other nodes reach this one directly.
keeps one port for every destinationMost home routers. Hole punching works.
changes the port per destinationMobile networks and carrier-grade NAT. IPv4 hole punching fails; IPv6 or a node reachable from outside helps.

sudo meshvpn doctor warns when a node has a hard NAT and no IPv6, and tells you what to change.

STEP 3

Open UDP 7870 where you can

One node that others can reach from outside is enough to give every node a direct path to it. Forward UDP port 7870 (and TCP 7870 for joining) on the router in front of a node, for example on a home router to the desktop, and allow it in cloud security groups.

Opening the port is safe in the sense that matters: a connection without the network key fails in the first handshake, before any traffic flows. Switch UDP off with udp = false in the configuration if you have to.

STEP 4

The machine can only make SSH connections

If a machine can reach some jump host over SSH, that is enough. meshvpn runs and supervises a reverse SSH tunnel and sends all its traffic through it:

on the firewalled machine
$ sudo meshvpn join mesh1-… --ssh user@jump.example.com --ssh-remote-port 7871

The daemon runs this for you and reconnects with backoff:

ssh -N -R :7871:127.0.0.1:7870 -D 127.0.0.1:1081 user@jump.example.com
  • Outgoing, the node reaches every other node through the SOCKS proxy of that same SSH connection. Nothing else has to be allowed.
  • Incoming, other nodes connect to jump.example.com:7871. That needs GatewayPorts clientspecified in the jump host's sshd_config. Without it the node still works: it connects out, and others reach it through relays.
  • SSH must log in without a password as root, or pass --ssh-identity /path/to/key. Other options: --ssh-port, --ssh-public-host, --ssh-no-socks.
Tunnel already managed elsewhere (autossh, for example)? Join with --no-outbound --endpoint jump:7871, then run sudo meshvpn connect jump.example.com:7871 on any node.

STEP 5

A public node for a network behind a firewall

Joining works by the new node dialing the addresses in the invite. If the network sits behind a corporate firewall, a node on the internet can't reach those addresses, but the network can reach it. Let the connection start from inside:

on the public node
$ sudo meshvpn join mesh1-… --name edge --endpoint 203.0.113.7:7870
$ sudo meshvpn up
on any node of the network
$ sudo meshvpn connect 203.0.113.7   # port 7870 is the default

The address is remembered, and gossip tells every other node about the public node. Until then, meshvpn status on the public node says that it can't reach the network and prints this command.

Keep in mind: a node on the internet can reach every service the other nodes offer on the mesh. Members are trusted.

STEP 6

Devices without internet access

Some devices can't reach the internet at all, but you can SSH into them from a jump host, often through an existing reverse tunnel such as localhost:2222. Install those from the jump host. Nothing is installed on the jump host itself:

on the jump host
$ curl -fsSL https://github.com/PlugOvr-ai/meshvpn/releases/latest/download/deploy.sh \
  | sh -s -- --invite mesh1-… user@localhost -p 2222

The script downloads the right binary, uploads it, installs it with sudo and joins the network. The device gets its own SSH key, which the script adds to your ~/.ssh/authorized_keys on the jump host with restrict,port-forwarding,command="echo meshvpn-ok": port forwarding only, no shell. Through that connection the device reaches the other nodes and GitHub for updates.

If the script can't work out how the device reaches the jump host, pass --jump user@host[:port]. Run it again to update the device.

STEP 7

Internet through another node

One node can offer its internet connection to the others, for example to appear with an office's address or to give machines without internet a way out:

$ sudo meshvpn exit offer     # on the node with the internet connection (kernel mode)
$ sudo meshvpn exit use office # on the nodes that should use it
$ meshvpn exit list            # who offers it, which one is used
$ sudo meshvpn exit off        # back to direct
  • All internet traffic of the machine goes through the exit. LANs, Docker networks, the mesh and replies to connections from outside stay direct, so an SSH session from the internet keeps working.
  • The exit forwards only to public internet addresses, never into its own LAN or to cloud metadata addresses. It needs iptables.
  • While the exit node is offline there is no internet, so nothing leaks out directly. DNS keeps using the machine's resolver, and IPv6 isn't carried.
