Use cases

Where hardware is shared, scarce or out of reach.

Five setups meshvpn is built for, with the commands that make them work. The companies in them are examples.

enterprise

Hardware-in-the-loop test benches

An automotive supplier has twelve benches: ECUs on HIL simulators, CAN rigs, a few prototypes. Developers in three cities and a contractor need them, and the nightly regression needs all of them at 22:00.

The benches join one network with the tag bench. A gateway in the lab accepts SSH from outside. Developers book what they need for the afternoon; the regression agent books tag:bench --count 12 every night. Nobody shares a password, nobody has a standing account on a bench, and the audit log shows who flashed which ECU when.

  • Exclusive bookings for flashing, shared ones for read-only monitoring
  • sudo during the booking, for drivers, can0 and udev rules
  • Contractors with only an SSH key: no VPN client on their side
  • Rules like "group:hil-team, at most 8 h"
Tutorial: book a test bench →
a day on the bench
# the rules, once
$ sudo meshvpn device add tag:bench --who group:hil-team --max 8h
$ sudo meshvpn gateway add gw-lab

# 13:00, two ECUs for the afternoon
$ sudo meshvpn book hil-ecu-01 hil-ecu-02 --user alice --for 5h

# the CAN rig, watched by two people
$ sudo meshvpn book can-rig-03 --user bob --for 3h --shared
$ sudo meshvpn book can-rig-03 --user carol --for 3h --shared

# 22:00, the regression takes every free bench
$ sudo meshvpn book tag:bench --count 12 --user regression \
      --from 2026-11-03T22:00+01:00 --for 6h
enterprise

AI compute clusters with agents

A research group runs eight GPU servers. People train models, and more and more AI agents run experiments on their own. Everyone wants "four A100 nodes, now", and at night half of the GPUs sit idle.

Long trainings go into the queue and run on every node nobody has booked. When a researcher books two nodes for the afternoon, the training on them saves its checkpoint and continues on two others, with the researcher's home and the name train42.mesh. The researcher logs in by that name as if it were their own workstation. Agents use the same queue with an API key, under the same rules.

  • Idle GPUs run queued jobs; bookings always get their nodes
  • Jobs resume from their checkpoint, on other nodes too, with the home and the name following
  • Agents and people under the same rules and the same log; meshvpn guide and an MCP server teach agents the commands
  • Datasets spread to all nodes at once with share and fetch

a training that never wastes a GPU

open source

Fleets behind firewalls

Raspberry Pis in customer buildings, measuring devices in the field, lab machines behind a university firewall. They can reach out, but nothing can reach them.

Each device joins over whatever it has: UDP through NAT, a reverse SSH tunnel to a jump host, or no internet at all and an install from the jump host. The fleet becomes one network with names. Update them in one go, run a command on all with exec, or open a desktop in the browser.

Tutorial: behind NAT and firewalls →
reaching the unreachable
# a device that may only SSH out
$ sudo meshvpn join mesh1-... --ssh tunnel@jump.example.com --ssh-remote-port 7871

# a device without internet, installed from the jump host
$ curl -fsSL https://github.com/PlugOvr-ai/meshvpn/releases/latest/download/deploy.sh \
    | sh -s -- --invite mesh1-... pi@localhost -p 2222

# then, for all of them
$ meshvpn exec tag:field -- uptime
enterprise · free for universities

Remote labs for teaching

A robotics course has ten robot arms and sixty students. Each lab group gets two hours a week on an arm, from home or from the lab.

Students are users with their SSH keys, lab groups are groups, and each group books its slot. The arm's controller gets a student account with sudo for those two hours, then it is locked again. Academic licenses are free for teaching and non-commercial research.

Academic licenses →
a semester
$ sudo meshvpn user add s4123 --key-file s4123.pub
$ sudo meshvpn group set group-07 s4123 s4188 s4202
$ sudo meshvpn device add tag:arm --who group:group-07 --max 2h
$ sudo meshvpn book arm-04 --user s4123 \
      --from 2026-11-05T14:00+01:00 --for 2h
open source

Distributed training across sites

Two GPU boxes in the office, one in a data center, one under a desk at home. Together they're a cluster, if they can find each other.

meshvpn finds the best path between each pair: the LAN where they share one, the mesh otherwise. meshvpn net env picks the settings NCCL needs, and meshvpn launch starts torchrun on every node and stops all of them if one fails.

Tutorial: distributed training →
four boxes, one job
$ meshvpn nodes tag:gpu
$ meshvpn net matrix --measure
$ meshvpn launch --gpus 2 tag:gpu -- torchrun train.py
